## 1 分钟项目介绍

我做的是一个带 Web 界面的个人 AI 助手。浏览器通过 WebSocket 和 Python 后端保持双向连接，前端把用户文本或音频输入发给后端，后端组织模型推理和工具调用，再用流式消息把文本、工具进度和语音结果推回页面。后端按职责拆成 Agent/推理、工具与权限、会话记忆、语音和认知等模块；另有一个 RAG 子系统包含分块、Embedding、混合检索和图处理能力。架构的重点是把交互实时性、工具执行安全和可扩展能力放进同一条运行链路。

## 2 请求链路

1. `__main__.py` 解析参数，启动 CLI Agent 或创建 FastAPI app。
2. 浏览器 `web_html/index.html` 按编号加载脚本；`02-utils.js` 等负责连接 WebSocket、消息状态和 UI。
3. 后端 `core/server.py` 接收消息并协调运行，把需要的推理放到合适的执行上下文。
4. Agent/推理引擎调用模型；模型提出工具调用时，经工具分发、权限检查和原生/MCP 执行，再把结果交回模型继续生成。
5. token/状态/工具结果经回调转为 WebSocket 消息，前端 `10-message-handler.js` 分发到消息 UI。
6. 启用语音时，ASR 输入和 TTS 输出进入对应的语音管理/路由模块；实际执行分支以当前代码和配置为准。

## 3 可以重点讲的设计取舍

- **WebSocket：**同一连接需要双向传输用户输入、音频、流式 token 和工具/状态事件；比请求完成后才返回更适合交互型界面。
- **Agent 与 CompanionAgent 分层：**把工具执行能力和人格化对话体验分开组合，避免 UI/人格逻辑全部塞进推理循环。
- **工具分发和权限：**工具执行集中路由并在执行前经过权限策略，便于接入 MCP 与新增工具，也提供确认/拒绝的控制点。
- **前端按功能拆模块：**共享 `state` 及加载顺序让模块轻量，但形成全局命名和加载顺序耦合；如果继续演进，可迁移 ES modules、加边界与类型约束。
- **多模态能力的代价：**ASR/TTS/桌面视觉带来更丰富交互，也增加模型依赖、资源占用、延迟、并发和错误恢复复杂度。

避免说“WebSocket 是唯一方案”“某参数一定是最佳值”“失败会自动回退”等绝对话，除非能用当前实现和测量数据证明。

## 5 面试前必须核实的源码风险

- `core/agent_team.py` 与其余项目 Python 文件的语法扫描已通过；服务启动还需先安装 FastAPI、uvicorn、OpenAI SDK 等基础依赖，再验证一条端到端请求。
- 根目录没有发现 `pyproject.toml`、`setup.py`、requirements 文件或 npm `package.json`。确认依赖如何安装、工作目录如何设置、密钥如何提供以及服务如何启动。
- `core/server.py` 非常大：分别定位 `/ws` 消息处理、HTTP API、生命周期、ASR/TTS、会话/技能路由；不要只背文件名。
- 核对全局单例和按连接状态：特别是模型客户端、Agent、Companion、ASR buffer、会话 ID、取消标志、音频结果是否跨客户端共享。
- 核对配置示例与密钥策略；仓库 README 曾含疑似 API Key 的命令，已从文档删去。检查它是否是真实凭据及是否仍出现在历史/其他文件中。
- 文档存在过时数字：前端是 19 个 JS 和 11 个 CSS 文件，旧文档仍有 15/9 的说法；逐篇文档需要进一步校正。
