# 项目架构详解

## 整体架构

芙芙是一个基于 **FastAPI + WebSocket** 的实时语音交互系统，采用前后端分离架构：

```
┌─────────────────────────────────────────────────────────────┐

│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
```

## 核心设计原则

### 1. 流式处理优先

所有耗时操作都采用流式处理，避免用户等待：

| 操作 | 流式实现 | 用户感知 |
|------|---------|---------|
| LLM 生成 | token_callback 实时推送 | 文字逐字出现 |
| TTS 合成 | 按句子分段，并行合成 | 边出文字边出声音 |
| ASR 识别 | 累积音频后批量识别 | 实时显示识别结果 |

### 2. 单例模式

全局只维护一个 Agent 实例和一个 CompanionAgent 实例（线程安全）：

```python
# server.py
_agent = None
_agent_lock = threading.Lock()

_companion = None
_companion_lock = threading.Lock()

def _get_agent():
    global _agent
    if _agent is None:
        with _agent_lock:
            if _agent is None:
                _agent = Agent(...)
    return _agent

def _get_companion():
    """CompanionAgent 始终创建，包装 Agent + AgentTeam。"""
    global _companion
    if _companion is None:
        with _companion_lock:
            if _companion is None:
                agent = _get_agent()
                team = AgentTeam(agent)
                _companion = CompanionAgent(agent=agent, agent_team=team)
    return _companion
```

**原因**：
- CosyVoice3 模型占用 ~4GB 显存，不能重复加载
- 多 WebSocket 连接共享同一 Agent，节省资源
- 对话历史全局管理，支持多轮对话

### 3. 延迟初始化

ASR/TTS 引擎按需加载，避免启动时阻塞：

```python
# agent.py
def _init_tts_router(self):
    if self._tts_router is None:
        self._tts_router = TTSEngineRouter(self.voice_provider_manager)
        # 如果本地模型存在，初始化本地引擎作为回退
        self._tts_router.init_local_engine(TTS_MODEL_PATH, ...)
```

**触发时机**：
- TTS：首次调用 `synthesize_speech()` 时（通过 TTSEngineRouter 选择远程/本地）
- ASR：前端点击麦克风按钮时

## 数据流详解

### 文本对话流程

```
用户输入 "你好"
    │
    ▼
前端发送 WebSocket 消息
    { type: "text", content: "你好", thinking: false }
    │
    ▼
server.py 接收，启动线程池执行
    response = loop.run_in_executor(None, _run_agent, ...)
    │
    ▼
CompanionAgent.process() 三阶段流程:
    │
    ├── Phase 1: 即时情感反应（环境感知 + 委派意识，直接 OpenAI 调用）
    │   token_callback("content", "哦，你好呀！让我看看~")
    │   → push_token → WebSocket stream_content
    │   续段信号：若为 [ANSWER] 类型，存入 phase1_pending_context/reaction
    │   → 下轮认知循环注入 ThoughtLoop 决策是否 speak 展开
    │
    ├── Phase 2: 委派 AgentTeam → agent.agent_loop()
    │   ├── _pre_analysis() 检测分析关键词，注入图谱提示
    │   ├── show_agent_team=True: 完整推送（正文+工具调用）
    │   └── show_agent_team=False: 不推送文本，TTS 分句仍正常
    │
    └── Phase 3: 结果总结（执行元数据注入，直接 OpenAI 调用）
        token_callback("content", "搞定啦！")
        → push_token → WebSocket stream_content
    │
    ▼
前端逐字收到 stream_content
```

### 流式 TTS 流程

```
LLM 生成 "你好，我是芙芙。今天天气很好。"
    │
    ▼
token_callback 逐字推送，同时累积到 sentence_buffer
    buffer: "你" → "你好" → "你好，" → ... → "你好，我是芙芙。"
    │
    ▼
检测到句子边界（"。"），启动 TTS worker 线程
    threading.Thread(target=_tts_worker, args=(0, "你好，我是芙芙")).start()
    │
    ▼
TTS worker 通过 TTSEngineRouter 合成（远程优先，失败自动回退本地）
    audio, source = agent.synthesize_speech("你好，我是芙芙")
    tts_results[0] = (audio, source)  # 存入结果字典 (含来源标识)
    │
    ▼
同时 LLM 继续生成下一句
    buffer: "今" → "今天" → ... → "今天天气很好。"
    │
    ▼
检测到第二个句子边界，启动第二个 TTS worker
    threading.Thread(target=_tts_worker, args=(1, "今天天气很好")).start()
    │
    ▼
LLM 生成完毕，触发 stream_end
    │
    ▼
server.py 按顺序等待 TTS 结果并推送
    for idx, _ in tts_tasks:
        while idx not in tts_results:
            await asyncio.sleep(0.1)
        audio_b64 = base64.b64encode(tts_results[idx]).decode()
        await _send_json(websocket, "stream_audio", audio_b64)
    │
    ▼
前端接收 stream_audio，加入播放队列
    enqueueAudio(base64Data)
    │
    ▼
顺序播放
    audioQueue: [audio0, audio1]
    playNextInQueue() → audio0.play() → onended → playNextInQueue() → audio1.play()
```

### ASR 识别流程

```
用户点击麦克风按钮
    │
    ▼
前端启动 MediaRecorder
    mediaRecorder = new MediaRecorder(stream, { mimeType: 'audio/webm;codecs=opus' })
    mediaRecorder.start(3000)  // 每 3 秒触发一次 ondataavailable
    │
    ▼
每 3 秒发送音频块
    { type: "audio", content: "<base64 webm>" }
    │
    ▼

    pcm_data = await _webm_to_pcm(audio_data)  # torchaudio.load + resample

    │
    ▼

    ▼
推送识别结果
    await _send_json(websocket, "asr_text", recognized)
    │
    ▼

    asrLiveText.textContent = state.asrAccumulated
```

## 关键技术选型

### 为什么选择 WebSocket 而非 HTTP SSE？

| 特性 | WebSocket | HTTP SSE |
|------|-----------|----------|
| 双向通信 | ✅ 支持 | ❌ 仅服务器→客户端 |
| 音频传输 | ✅ 支持二进制 | ❌ 仅文本 |
| 连接开销 | 低（持久连接） | 中（需轮询或重连） |
| 浏览器支持 | 广泛 | 广泛 |

**结论**：WebSocket 是唯一选择，因为需要：
- 客户端发送音频（ASR）
- 服务器推送音频（TTS）
- 实时双向状态同步

### 为什么 TTS 使用后台线程而非 asyncio？

```python
# 方案 1: asyncio (错误)
audio = await agent.synthesize_speech(text)  # 阻塞事件循环！

# 方案 2: 后台线程 (正确)
threading.Thread(target=_tts_worker, ...).start()
```

**原因**：
- CosyVoice3 推理是 **CPU/GPU 密集型**，单次合成耗时 2-5 秒
- 如果在事件循环中执行，会阻塞所有 WebSocket 消息
- 后台线程可以并行合成多个句子，提升吞吐量

### 为什么 ASR 累积 6 秒才识别？

| 音频长度 | dashscope 识别效果 | 原因 |
|---------|-------------------|------|
| 3 秒 | ❌ 差 | 上下文不足，误识别率高 |
| 6 秒 | ✅ 好 | 足够识别完整句子 |
| 10 秒 | ✅ 好 | 但延迟过高 |

**权衡**：6 秒是准确性和实时性的最佳平衡点。

## 线程安全设计

### 问题场景

```python
# server.py
def push_token(token_type, text):
    # 在线程池中运行，需要线程安全地推送 WebSocket 消息
    asyncio.run_coroutine_threadsafe(
        _send_json(websocket, "stream_content", text),
        loop
    )
```

**风险**：
- `push_token` 在线程池线程中执行
- `_send_json` 是 async 函数，必须在事件循环中执行
- 直接调用会导致 `RuntimeError: no current event loop`

### 解决方案

```python
# 使用 run_coroutine_threadsafe 跨线程调度
asyncio.run_coroutine_threadsafe(coro, loop)
```

**工作原理**：
1. 线程池线程调用 `run_coroutine_threadsafe`
2. 将协程提交到事件循环的任务队列
3. 事件循环线程执行协程
4. 返回 `concurrent.futures.Future`（可选等待结果）

### TTS 结果字典的线程安全

```python
tts_results = {}
tts_lock = threading.Lock()

def _tts_worker(index, sentence):
    audio, source = agent.synthesize_speech(sentence)
    with tts_lock:  # 互斥锁保护
        tts_results[index] = (audio, source)
```

**为什么需要锁**：
- 多个 TTS worker 线程并发写入 `tts_results`
- Python 的 GIL 只保证原子操作（如 `dict[key] = value`）
- 但 `if key in dict` + `dict[key]` 组合操作不是原子的

## 错误处理策略

### LLM API 失败

```python
# agent.py
try:
    stream = self.client.chat.completions.create(...)
except Exception as e:
    if token_callback:
        token_callback("error", f"LLM 调用失败: {e}")
    return None
```

**处理流程**：
1. 捕获异常，避免服务器崩溃
2. 通过 `token_callback` 通知前端
3. 前端显示错误消息，用户可重试

### TTS 合成失败

```python
# server.py
audio, source = agent.synthesize_speech(sentence)
if audio:
    tts_results[index] = (audio, source)
# 失败时静默跳过，不阻塞其他句子
# 远程失败 + fallback=True 时自动回退本地，source="fallback"
```

**处理流程**：
1. 单个句子合成失败不影响整体
2. 远程 TTS 失败时，TTSEngineRouter 自动回退到本地引擎（如果开启了 fallback）
3. 回退时通过 WebSocket `status` 消息通知前端："⚠ 远程 TTS 不可用，已回退到本地引擎"
4. 前端等待超时时跳过该音频
5. 用户可能感知到某句话没有语音，但文字仍正常显示

### WebSocket 断开

```python
# server.py
try:
    async for message in websocket:
        ...
except WebSocketDisconnect:
    print("WebSocket disconnected")
```

**处理流程**：
1. 捕获 `WebSocketDisconnect`，清理资源
2. 前端检测到连接断开，显示提示
3. 用户刷新页面重新连接

## 性能优化

### 1. Markdown 清洗正则缓存

```python
# 预编译正则表达式
RE_THINK = re.compile(r'<think>.*?</think>', re.DOTALL)
RE_CODE_BLOCK = re.compile(r'```[\s\S]*?```')
RE_INLINE_CODE = re.compile(r'`[^`]+`')

# 使用
clean = RE_THINK.sub('', text)
```

**收益**：避免每次调用时重新编译正则，提升 10-20% 性能。

### 2. 音频 Base64 编码优化

```python
# 方案 1: 多次转换 (慢)
audio_b64 = base64.b64encode(audio_bytes.tobytes()).decode()

# 方案 2: 直接编码 (快)
audio_b64 = base64.b64encode(audio_bytes).decode()
```

**收益**：减少一次内存拷贝，提升 5-10% 编码速度。

### 3. 句子分段算法

```python
sentence_boundary = set("。！？.!?")

if text[-1] in sentence_boundary:
    # 触发 TTS（通过 TTSEngineRouter 自动选择远程/本地引擎）
```

**设计决策**：
- 仅使用句末标点（`。！？.!?`）作为分段点，**不包含** `\n`、`；`、`;`
- 原因：LLM 输出常含 markdown 表格行、列表项、标题等，换行触发会导致碎片文本被合成
- `set` 查找时间复杂度 O(1)

### 4. TTS 内容清洗

合成前对文本进行 12 步清洗，去除 markdown 格式和非自然语言内容。清洗逻辑已提取为模块级函数 `_clean_tts_text(text) -> str`，供 `push_token`（正常推送）和 `tts_only_token_callback`（隐藏 AgentTeam 链路时仅做 TTS 分句）共享：

| 步骤 | 清洗内容 | 示例 |
|------|----------|------|
| 1 | `<think>...</think>` 标签 | 思考过程标签 |
| 2 | ` ```...``` ` 代码块 | 整段代码 |
| 3 | `` `code` `` 行内代码 | 变量名、函数名 |
| 4 | `[text](url)` 链接 | 保留 text，去除 url |
| 5 | `**bold**` 粗体 | 保留文字，去除星号 |
| 6 | `*italic*` 斜体 | 保留文字 |
| 7 | `# heading` 标题符号 | 去除 #、*、- 前缀 |
| 8 | `| col | col |` 表格行 | 整行去除 |
| 9 | `|---|---|` 表格分隔 | 整行去除 |
| 10 | emoji 字符 | 👋📖💻 等 |
| 11 | URL 链接 | `https://...` |
| 12 | 多余空白 | 合并为单空格 |

**过滤阈值**：清洗后有效字符（中文/字母/数字）≥ 4 才触发合成，避免碎片文本（如 `OK`、`No`）产生无意义语音。

## 总结

芙芙的核心架构围绕 **流式处理** 和 **实时交互** 设计：

1. **WebSocket 双向通信**：支持文本、音频、状态的实时传输
2. **CompanionAgent 三阶段流程**：环境感知 + 情感反应（短回复治理：recency bias 末尾 system reminder + 对抗性 few-shot）→ AgentTeam 委派（含预分析）→ 执行元数据总结，伴侣层始终存在
3. **认知循环续段机制**：Phase 1 完成后通过 `phase1_pending_context` / `phase1_pending_reaction` 信号字段引导 ThoughtLoop 决策是否 speak 展开
4. **自主执行进度外显**：自主行动期间通过 `cognitive_thought`(mode="act") 推送琥缀色气泡，3 秒节流防刷屏
5. **AgentTeam 链路可见性**：默认隐藏执行过程，可切换显示完整工具调用链路
6. **知识图谱集成**：7 个原生工具（4 基础 + 3 图谱），基于 graphify AST API 零 LLM 成本分析代码结构
7. **流式 LLM + 流式 TTS**：边生成文字边合成语音，大幅减少等待时间
8. **TTS 路由 + 自动回退**：远程 GPU 服务优先，失败自动回退本地引擎
9. **单例模式 + 延迟初始化**：Agent 和 CompanionAgent 各一个全局单例，节省资源
10. **lifespan 生命周期**：替代废弃的 `on_event`，使用 `asynccontextmanager` 管理启动/关闭
11. **线程安全设计**：使用 `run_coroutine_threadsafe` 和互斥锁
12. **优雅的错误处理**：单个组件失败不影响整体体验

这套架构可以扩展到更多场景：
- 多用户并发（每个 WebSocket 连接独立的 `stop_push` 标志）
- 多模型切换（配置化的 LLM 客户端）
- 多 TTS 引擎（远程 CosyVoice 服务 + 本地回退 + TTSEngineRouter 路由）
