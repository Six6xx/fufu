# 代理框架工程的哲学

> **模型本身已经知道如何成为一个代理。你的任务是为它构建一个值得行动的世界。**

## 根本真理

剥去所有框架、所有库、所有架构模式，还剩下什么？

一个循环。一个模型。一份行动的邀请。

代理不是代码。代理就是模型本身——一个在人类集体的问题解决、推理和工具使用数据上训练而成的巨大神经网络。代码只是为模型提供表达其自主性的机会。

代码是**框架（harness）**，模型才是**代理（agent）**。二者不可互换。若混淆它们，你就会构建错误的东西。

## 代理是什么

代理是一个神经网络——Transformer、RNN 或其他学习函数——通过在动作序列数据上进行数十亿次梯度更新训练而成，能够感知环境、推理目标，并采取行动以达成目标。

人类是代理：由进化塑造的生物神经网络。DeepMind 的 DQN 是代理：从原始像素学会玩 Atari 游戏的卷积网络。OpenAI Five 是代理：通过自我对弈学会 Dota 2 团队协作的五个网络。Claude 是代理：从人类知识广度中学会推理与行动的语言模型。

在所有这些案例中，代理都是那个经过训练的模型，而不是游戏引擎、Dota 2 客户端或终端。代理就是模型本身。

## 代理不是什么

提示词管道（prompt plumbing）不是代理。用 if-else 分支、节点图或硬编码路由逻辑把 LLM API 调用拼接在一起，并不会产生真正的代理。那只会造出脆弱的流水线——一种把 LLM 塞进去充当文本补全节点的鲁布·戈德堡机械装置（Rube Goldberg machine）。

你无法靠工程手段“制造”出代理性（agency）。代理性是学来的，而非编程写出来的。再多的胶水代码也无法涌现出自主行为。这类系统不过是现代版的“老式人工智能”（GOFAI）——几十年前就被领域抛弃的符号规则系统，如今只不过被喷上了 LLM 的外衣。

## 框架：我们真正构建的东西

如果模型是代理，那么代码是什么？它是**框架**——为代理在其特定领域中感知和行动所提供的环境。

```
框架 = 工具 + 知识 + 观测 + 行动接口 + 权限
```

### 工具：代理的双手

工具回答：**代理能做什么？**

每个工具都是代理在其环境中可执行的原子操作：文件读写、Shell 执行、API 调用、浏览器控制、数据库查询等。模型需要理解每个工具的作用，但无需预先知道如何编排它们——它自己会想出来。

**设计原则**：原子性、可组合性、描述清晰。从 3–5 个工具开始。仅当模型因缺少某个工具而持续无法完成任务时，才添加更多。

### 知识：代理的专业能力

知识回答：**代理知道什么？**

将通用代理转变为领域专家所需的专业知识：产品文档、架构决策、法规要求、风格指南等。应通过 tool_result 按需注入，而非一开始就塞进系统提示词。渐进式披露（progressive disclosure）能为真正重要的内容保留上下文空间。

**设计原则**：可用但不强制。代理应知道有哪些知识存在，并按需拉取。

### 上下文：代理的记忆

上下文是将单个动作串联成连贯行为的线索：说过什么、尝试过什么、学到什么、决定过什么。

**设计原则**：上下文极其宝贵，必须加以保护。隔离会产生噪音的子任务（s04），历史过长时进行压缩（s06），让目标能跨越单次对话持久存在（s07）。

### 权限：代理的边界

权限回答：**代理被允许做什么？**

沙箱化文件访问、破坏性操作需审批、在代理与外部系统之间建立信任边界——这正是安全工程与框架工程交汇之处。

**设计原则**：约束聚焦行为，而非限制能力。“一次只能有一个任务处于 in_progress 状态”强制顺序专注；“只读子代理”防止意外修改。

### 任务-过程数据：代理的训练信号

代理在你的框架中执行的每一个动作序列，都是训练信号。真实部署中产生的感知-推理-行动轨迹，正是用于微调下一代代理模型的原始材料。你的框架不仅服务于代理，还能帮助其进化。

## 通用循环

无论领域如何，每个有效的代理都遵循相同的模式：

```
循环：
  模型看到：对话历史 + 可用工具
  模型决定：执行动作 或 返回回复
  若执行动作：工具被调用，结果加入上下文，继续循环
  若返回回复：答案输出，循环结束
```

这并非简化，而是真实架构。其余一切皆为框架工程——叠加在此循环之上的机制，旨在让代理更高效。循环属于代理，机制属于框架。

## 框架工程原则

### 信任模型

最重要的原则：**信任模型**。

不要试图预判每个边缘情况，不要构建复杂的决策树，不要预先规定工作流。

模型的推理能力远超你能写出的任何规则系统。你的条件逻辑会在边缘情况下失效，而模型却能推理应对。

**给模型工具和知识，让它自己决定如何使用。**

### 约束赋能

这看似矛盾，但约束并不会限制代理——反而使其聚焦。

“一次只能有一个任务进行中”的待办列表强制顺序专注；“只读子代理”防止意外修改；上下文压缩阈值避免历史信息淹没当前任务。

最好的约束防止模型迷失方向，而非微观管理其方法。

### 渐进复杂性

切勿一开始就构建全部功能。

```
第 0 层：模型 + 一个工具（bash）               -- s01
第 1 层：模型 + 工具分发映射                    -- s02
第 2 层：模型 + 规划                            -- s03
第 3 层：模型 + 子代理 + 技能                   -- s04, s05
第 4 层：模型 + 上下文管理 + 持久化             -- s06, s07, s08
第 5 层：模型 + 团队 + 自主性 + 隔离            -- s09-s12
```

从可能奏效的最低层级开始。只有当实际使用暴露出需求时，才向上演进。

## 思维转变

构建框架需要根本性的思维转变：

**从**：“我如何让系统做 X？”  
**到**：“我如何让模型有能力做 X？”

**从**：“当用户说 Y 时会发生什么？”  
**到**：“哪些工具能帮助应对 Y？”

**从**：“这个任务的工作流是什么？”  
**到**：“模型需要什么才能自己推导出工作流？”

**从**：“我在构建一个代理。”  
**到**：“我在为代理构建一个框架。”

最好的框架代码几乎平淡无奇：简单的循环、清晰的工具定义、干净的上下文管理。魔法不在代码中——而在模型里。

## 载具隐喻

模型是驾驶员，框架是载具。

编码代理的载具是它的 IDE、终端和文件系统；农业代理的载具是传感器阵列、灌溉控制系统和天气数据；酒店代理的载具是预订系统、客户沟通渠道和设施 API。

驾驶员具备泛化能力，载具则专精于特定领域。作为框架工程师，你的任务是为你的领域打造最佳载具——赋予驾驶员最大可见性、精准控制力和清晰边界。

打造驾驶舱、仪表盘和操控装置。飞行员早已训练有素。

## 结论

模型是代理，代码是框架。清楚你正在构建的是哪一个。

你不是在编写智能，而是在构建智能所栖居的世界。这个世界质量的高低——代理感知的清晰度、行动的精确度、知识的丰富度——直接决定了智能能多有效地展现自身。

构建卓越的框架，剩下的交给代理。
